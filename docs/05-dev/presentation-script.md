## 02 · 5 คำถามที่จะตอบวันนี้
*เวลาโดยประมาณ 0:30*

บอกโครงการนำเสนอเป็น 5 คำถาม:
1) ที่ตั้ง — โรงแรมอยู่ที่ไหน
2) ลักษณะโรงแรมและบริการ

## 07 · Tech stack และสิ่งที่รันใน Docker
*เวลาโดยประมาณ 1:00*

Tech stack แบ่ง 4 กลุ่ม:
- หน้าเว็บ: Next.js 16.4 (App Router) + React 19.3 + Ant Design 6.6 เขียนด้วย TypeScript ทั้งระบบ
- เซิร์ฟเวอร์: Next.js Route Handlers รันบน Node.js 20 · คุยกับฐานข้อมูลด้วย pg (node-postgres) เขียน SQL เอง ไม่ใช้ ORM ทุก query เป็น parameterized · Zod ตรวจข้อมูลที่ส่งเข้ามา · login พนักงานด้วย JWT ใน cookie (jose) และ hash รหัสผ่านด้วย bcryptjs
- ฐานข้อมูล: PostgreSQL 17 — schema, triggers, views และข้อมูลตั้งต้นอยู่ในไฟล์ SQL (db/schema, db/seed) มีเทสต์กฎธุรกิจ 58 ข้อ (npm run db:test)
- เครื่องมือ: ESLint, Git + GitHub, npm scripts

คำถาม “รันผ่าน Docker ไหม”: ตอบว่าใช้ Docker สำหรับฐานข้อมูล — docker-compose.yml มี service เดียวคือ postgres:17-alpine ตั้ง timezone Asia/Bangkok เปิด port 5433 และเก็บข้อมูลใน volume ชื่อ hotel-pgdata สั่งด้วย npm run db:up (มี healthcheck รอจนพร้อม) ส่วนตัวเว็บ Next.js ยังรันบนเครื่องด้วย npm run dev ไม่ได้ทำเป็น container — ถ้าจะ deploy จริงค่อยเพิ่ม Dockerfile ของเว็บ

ทำไมใช้ Docker กับฐานข้อมูล: ทุกคนในกลุ่มได้ PostgreSQL เวอร์ชันเดียวกัน ตั้งค่าเหมือนกัน ไม่ต้องติดตั้งลงเครื่อง และล้างสร้างใหม่ได้ด้วย npm run db:reset

เดโม: เปิด terminal → docker ps ให้เห็น container hotel-advdb-postgres กำลังรัน

## 08 · ระบบโรงแรม 3 สาขา ที่ฐานข้อมูลคุมกฎเอง
*เวลาโดยประมาณ 1:00* · **เปิดเว็บ → login เป็น OWNER (owner@hotel.local) · หน้า Dashboard**

ประเด็นเดียวของหน้านี้: กฎของธุรกิจอยู่ในฐานข้อมูล ไม่ได้อยู่ในหน้าเว็บ

- หน้าเว็บใช้ Ant Design มี 24 เมนูใน 7 โมดูล เมนูที่เห็นขึ้นกับสิทธิ์
- API ทุกตัวผ่าน route() ที่ตรวจ permission และทุกการเขียนอยู่ใน transaction (withTx) ซึ่งบอก trigger ด้วยว่าพนักงานคนไหนเป็นคนทำ
- PostgreSQL คือคนตัดสินสุดท้าย: CHECK, UNIQUE, EXCLUDE และ 44 triggers ที่บังคับกฎ R1–R22
- ใช้ raw SQL (pg) แทน ORM เพราะวิชานี้ต้องโชว์ constraint, trigger, view และ transaction ให้เห็นชัด

เดโม: login เป็น owner@hotel.local (รหัส Hotel@1234) → ชี้เมนู 7 กลุ่มทางซ้าย และตัวเลือก “All branches” บน header → Dashboard ดึงจาก view v_dashboard_branch_today

“จุดบอด” ในที่นี้คือปัญหาที่โรงแรมหลายสาขาเจอเมื่อจัดการด้วยสมุดหรือ Excel แยกสาขา และระบบเราปิดไว้อย่างไร:

1) จองห้องซ้อน — โดยเฉพาะตอนสองเคาน์เตอร์กดพร้อมกัน: trigger R3 ล็อกแถวห้องก่อนตรวจวันทับ
2) ข้อมูลสาขาปนกัน — ทุก query กรองด้วย branchScope ของ session และ R16 บังคับว่าคนที่ถูกมอบงานต้องอยู่สาขาเดียวกับงาน
3) ราคาเปลี่ยนแล้วบิลเก่าเพี้ยน — ใบจองเก็บราคา ณ วันจองไว้ (snapshot)
4) ยอดเงินคลาดเคลื่อน — trigger คำนวณยอดรวมและส่วนลด (สมาชิกซ้อนโปร) เอง และ R17 กันรับเงินหรือคืนเงินเกินยอด
5) ไม่รู้ว่าใครทำ — FK ชี้ไปพนักงานที่ทำรายการ และทุกการเปลี่ยนสถานะใบจองถูกบันทึกลง booking_status_log
6) ห้องที่ซ่อมอยู่ — R15 ทำให้ห้องที่มีงานซ่อมค้างเป็น MAINTENANCE เช็คอินไม่ได้ และเช็คเอาท์แล้วก็ไม่กลับเป็นห้องว่างจนกว่าจะซ่อมเสร็จ
7) มอบงานผิดคน — R5 ต้องมีทักษะ R16 ต้องอยู่สาขาเดียวกัน

ประเด็นสำคัญ: กฎอยู่ในฐานข้อมูล ไม่ได้อยู่แค่หน้าเว็บ จึงกันได้แม้มีคนเข้าฐานข้อมูลตรง ๆ หรือหน้าเว็บมีบั๊ก — รายละเอียดว่าทำยังไงอยู่ในหัวข้อ 5 หน้า “สิ่งที่ FK บังคับไม่ได้”

## 10 · จุดบอดที่ยังเหลือ และทางไปต่อ
*เวลาโดยประมาณ 1:00*

พูดตรง ๆ ว่ายังเหลืออะไร และบอกทางไปต่อ:

1) เว็บฝั่งลูกค้า — ตาราง CUSTOMER มี password_hash, BOOKING มี booking_channel = WEBSITE และ created_by_emp_id เป็น NULL ได้ แปลว่า schema พร้อม ที่ขาดคือหน้าเว็บ ระบบ login ลูกค้า และ API ฝั่งลูกค้า (มีต้นแบบหน้าจอแล้วแต่ยังเป็นข้อมูลจำลอง)
2) ชำระเงิน — ตอนนี้พนักงานบันทึกการรับเงินเอง (สลิป เลขอ้างอิง) ยังไม่ต่อ payment gateway
3) OTA — ใบจองจาก OTA ต้องคีย์เข้าระบบเอง ฐานข้อมูลยังกันจองซ้อนในระบบได้ แต่ถ้า OTA ขายไปก่อน เราจะรู้ตอนคีย์
4) ข้อมูลไม่ครบ — เจอจริงตอนทดสอบ: เพิ่มห้อง Suite ที่ CNX ผ่านหน้า Rooms ได้ แต่ CNX ไม่มีเรทของ Suite ห้องนั้นจึงจองไม่ได้ ฐานข้อมูลทำถูก (ไม่ให้จองห้องที่ไม่มีราคา) แต่ไม่มีหน้าจอเตือนผู้ดูแลว่ามีห้องที่ขายไม่ได้ (หลัง db:reset ห้องทดสอบนี้จะหายไป เพราะไม่ได้อยู่ใน seed)
5) รายงาน — ตอนนี้มี 3 views ยังไม่มีรายงานรายได้หรืออัตราการเข้าพักย้อนหลัง
6) ความทนทาน — ฐานข้อมูลตัวเดียว ยังไม่ทำ backup อัตโนมัติ, replication หรือ failover ซึ่งเป็นงานต่อของระบบจริง

ถ้าถูกถามเรื่องเทสต์: เทสต์บางข้อ (R21/R22) อิงวันที่ปัจจุบัน ต้องรัน npm run db:reset ก่อน db:test ให้ข้อมูลตรงวัน

## 11 · 7 โมดูล ไหลจาก ตั้งค่า → จอง → งานที่ตามมา
*เวลาโดยประมาณ 1:00* · **เปิดเว็บ → ชี้เมนูทางซ้าย ที่จัดกลุ่มตาม 7 โมดูลนี้**

อ่านผังจากบนลงล่าง:

1) ตั้งค่า (master data): องค์กร/สิทธิ์ (A) ห้องพัก (C) ระดับสมาชิกและโปรโมชัน (G) แคตตาล็อกบริการ (E) — ข้อมูลที่ตั้งครั้งเดียวแล้วใช้ซ้ำ
2) ธุรกรรมหลัก: ทุกอย่างไหลเข้า BOOKING (D) — ลูกค้า → ใบจอง → ห้องในใบจอง → ผู้เข้าพัก ส่วนกำลังคน (B) ห้อยจาก EMPLOYEE ใน A
3) งานที่ตามมาหลังจอง: สั่งบริการ (E) การชำระเงินและรีวิว (G) ส่วนงานหน้างาน (F) ผูกกับ ROOM

ข้อสังเกต: EMPLOYEE ถูกอ้างถึง 14 จาก 49 FK — เพราะระบบบันทึกว่า “ใครเป็นคนทำ” ในเกือบทุกงาน (จะลงรายละเอียดในหน้า workforce)

เดโม: ชี้เมนูทางซ้ายว่าเรียงตาม 7 โมดูลนี้

## 13 · ความสัมพันธ์ 6 แบบ ที่ใช้ในระบบนี้
*เวลาโดยประมาณ 1:30*

หน้านี้คือ “ภาษา” ที่จะใช้อ่านผังในหน้าต่อ ๆ ไป อธิบายสั้น ๆ ทีละการ์ด:

1) 1 : N — แบบที่เยอะที่สุด เช่น สาขามีหลายห้อง
2) M : N — ฐานข้อมูลเก็บตรง ๆ ไม่ได้ ต้องมีตารางกลาง ระบบนี้มี 4 ตาราง: ROLE_PERMISSION, ROOM_TYPE_AMENITY, BRANCH_SERVICE, EMPLOYEE_SERVICE_SKILL
3) 1 : 0..1 — ทำโดยตั้ง FK ฝั่งลูกเป็น UNIQUE เช่น ใบจองหนึ่งใบรีวิวได้ครั้งเดียว และ ATTENDANCE หนึ่งแถวต่อตารางเวรหนึ่งแถว
4) Self-reference — EMPLOYEE.manager_id ชี้กลับมาที่ EMPLOYEE เพื่อเก็บว่าใครเป็นหัวหน้าใคร
5) Optional FK — FK ที่เป็น NULL ได้มีความหมาย เช่น created_by_emp_id เป็น NULL แปลว่าลูกค้าจองเองทางเว็บ (booking_channel = WEBSITE) และ owner คือ EMPLOYEE ที่ branch_id เป็น NULL
6) Actor FK — 10 จาก 49 FK มีไว้บอกว่าใครเป็นคนทำ (รับเงิน เช็คอิน อนุมัติ ฯลฯ) ใน ERD วาดเป็นเส้นประ

## 14 · ทุกอย่างผูกกับสาขา
*เวลาโดยประมาณ 1:30* · **เปิดเว็บ → เลือก BKK บน header แล้วเปิด Rooms / Bookings · คลิกแถว BKK ใน Branches**

BRANCH คือตารางแม่ที่ลูกเยอะที่สุด (7 ตาราง) ทำให้ทั้งระบบแยกข้อมูลตามสาขาได้

- EMPLOYEE.branch_id เป็น NULL ได้ — owner เป็นพนักงานระดับเครือ ไม่สังกัดสาขา (กฎ R2)
- ราคาห้อง (ROOM_RATE) และราคาบริการ (BRANCH_SERVICE) แยกตามสาขา สาขาต่างกันราคาต่างกันได้

จุด Advanced: ใบจองไปถึงสาขาได้ 2 เส้นทาง คือ BOOKING.branch_id ตรง ๆ และผ่าน BOOKING_ROOM → ROOM → BRANCH สองทางนี้ต้องได้คำตอบเดียวกัน FK ทำเรื่องนี้ไม่ได้ trigger R3 จึงตรวจตอนเพิ่มห้องเข้าใบจอง (และ R4 ทำแบบเดียวกันกับบริการ)

เดโม:
1) เลือก BKK บน header → เปิด Rooms และ Bookings ให้เห็นว่าเหลือแต่ BKK (กรองที่ server ด้วย branchScope)
2) เปิด Branches → คลิกแถว BKK → ชี้จำนวนห้อง พนักงาน และใบจองที่ active
3) กลับไปเลือก All branches

## 15 · สิทธิ์เป็นข้อมูลในตาราง ไม่ใช่ if ในโค้ด
*เวลาโดยประมาณ 1:30* · **เปิดเว็บ → Roles & Permissions · แล้ว login staff.bkk เปิด /branches → 403**

สิทธิ์ไม่ได้เขียนเป็น if ในโค้ด แต่เก็บเป็นข้อมูล: PERMISSION มี 30 รหัส (ตามหน้าจอ) ROLE มี 3 แบบ (OWNER, MANAGER, STAFF) และ ROLE_PERMISSION เป็นตารางกลางที่จับคู่กัน

- ROLE_PERMISSION ใช้ composite PK (role_id, permission_id) → ให้สิทธิ์เดิมซ้ำไม่ได้ และผ่าน 2NF เพราะ granted_at ขึ้นกับทั้งคู่
- ROLE.scope_level = CHAIN หรือ BRANCH; กฎ R2 บังคับว่า role ระดับเครือห้ามมีสาขา ส่วน role ระดับสาขาต้องมีสาขา
- EMPLOYEE.manager_id อ้างถึงตัวเอง (self-reference) และ R2b บังคับให้หัวหน้าอยู่สาขาเดียวกัน
- R20: ระบบต้องเหลือคนที่จัดการสิทธิ์ได้อย่างน้อย 1 คนเสมอ ป้องกันการล็อกตัวเองออก

เดโม:
1) เปิด Roles & Permissions ให้เห็น matrix สิทธิ์
2) Sign out → login staff.bkk@hotel.local → พิมพ์ URL /branches → ได้ 403 (API ก็ตอบ 403 เช่นกัน)

## 16 · ห้องพัก: ราคาผูกกับสาขา + ประเภท
*เวลาโดยประมาณ 1:00* · **เปิดเว็บ → Rooms › BKK 301 (รูป · amenities · current rate) · แล้วเปิด Room rates**

ห้องหนึ่งห้องต้องรู้ 4 อย่าง: อยู่สาขาไหน เป็นประเภทอะไร มีสิ่งอำนวยความสะดวกอะไร และราคาเท่าไร

- ROOM มีแม่ 2 ตาราง: BRANCH และ ROOM_TYPE
- สิ่งอำนวยความสะดวกผูกกับ “ประเภทห้อง” ไม่ใช่รายห้อง และเป็น M:N จึงมีตารางกลาง ROOM_TYPE_AMENITY (ร่างแรกเก็บเป็นข้อความยาวช่องเดียว ซึ่งผิด 1NF)
- ราคา (ROOM_RATE) ผูกกับ (สาขา, ประเภทห้อง, ช่วงวัน) ไม่ได้ผูกกับห้อง — ห้อง Deluxe ทุกห้องในสาขาเดียวกันราคาเท่ากัน
- R1 ใช้ EXCLUDE constraint (gist + daterange) กันไม่ให้ช่วงวันของเรทในสาขาและประเภทเดียวกันทับกัน
- partial unique index: ห้องหนึ่งมีรูปปกได้รูปเดียว
- R3d: ถ้าห้องมีใบจองค้างอยู่ เปลี่ยนสาขาหรือประเภทห้องไม่ได้ เพราะจะทำให้ใบจองเดิมผิด

เดโม: Rooms → คลิก BKK ห้อง 301 → เปิดรูป, amenities, current rate → กลับไปชี้ status → เปิด Room rates

## 17 · ใบจองหนึ่งใบ แตกเป็นหลายตาราง
*เวลาโดยประมาณ 2:00* · **เปิดเว็บ → Bookings › BK-0001 · ชี้ rooms, guests, services, payments และ status timeline**

หน้านี้สำคัญที่สุด ใช้เวลามากที่สุดได้

ฝั่งซ้าย อ่านเป็นลำดับชั้น:
- MEMBER_TIER → CUSTOMER: ระดับสมาชิกขยับตามแต้มเอง (trigger R13) ไม่ให้แอปเขียน tier_id ตรง ๆ
- CUSTOMER → BOOKING: ลูกค้าหนึ่งคนจองได้หลายใบ
- BOOKING → BOOKING_ROOM: ใบจองหนึ่งใบมีได้หลายห้อง และเก็บเวลาเช็คอินจริงรายห้อง
- BOOKING_ROOM → GUEST: เก็บผู้เข้าพักรายคน แขกหลักได้คนเดียวต่อห้อง (partial unique)
- BOOKING_ROOM ชี้ไป ROOM และ ROOM_RATE และ copy ราคามาเก็บไว้ (price_per_night) — ถ้าวันหลังแก้เรท ใบจองเก่าไม่เปลี่ยน

ฝั่งขวา คือตารางลูกอื่นของ BOOKING: การชำระเงิน บริการที่สั่ง รีวิว (ได้ครั้งเดียว) และ audit log ที่ trigger เขียนให้ทุกครั้งที่สถานะเปลี่ยน

ยอดเงิน 4 ช่องใน BOOKING (room_total, service_total, discount_amount, grand_total) คำนวณโดย trigger เท่านั้น

เดโม: เปิด Bookings → BK-0001 → ชี้ rooms, guests, services, payments, status timeline และปุ่ม check-in/check-out (ทำใน transaction เดียว)

## 18 · SERVICE ตัวเดียว ต่อออกเป็น 4 ความสัมพันธ์
*เวลาโดยประมาณ 1:30* · **เปิดเว็บ → Service orders › assign พนักงาน · แล้วเปิด Skills**

การตัดสินใจหลักของโมดูลนี้: ไม่แยก “บริการของพนักงาน” กับ “บริการของลูกค้า” เป็นคนละตาราง — SERVICE เป็น master ตัวเดียว แล้วแตกเป็นตารางกลางตามบทบาท

1) BRANCH_SERVICE (BRANCH ↔ SERVICE): สาขาไหนเปิดขายบริการอะไร ราคาสาขา และเวลาเปิด–ปิด
2) BOOKING_SERVICE (BOOKING ↔ BRANCH_SERVICE): ลูกค้าสั่งอะไร จำนวน และราคา ณ วันสั่ง (unit_price เป็น snapshot) — R4 บังคับว่าต้องเป็นบริการของสาขาเดียวกับใบจอง
3) EMPLOYEE_SERVICE_SKILL (EMPLOYEE ↔ SERVICE): ใครทำบริการไหนเป็น และระดับทักษะ
4) SERVICE_ASSIGNMENT (BOOKING_SERVICE ↔ EMPLOYEE): ใครลงมือทำออเดอร์ไหน เริ่ม–เสร็จเมื่อไร คะแนนคุณภาพ

กฎที่ FK บังคับเองไม่ได้:
- R5: คนที่ถูก assign ต้องมีแถวคู่ (employee, service) ใน EMPLOYEE_SERVICE_SKILL — เส้นประในผัง
- R6: ออเดอร์หนึ่งบรรทัดมีคนทำที่ active ได้คนเดียว (partial unique index) เปลี่ยนคนทำ = insert แถวใหม่และตั้งแถวเดิมเป็น REASSIGNED ไม่ update ทับ จึงเห็นประวัติครบ

เดโม: Service orders → เปิดออเดอร์ → assign พนักงาน → เปิด Skills ให้เห็นว่าคนที่ assign ได้ต้องมีทักษะนั้น (ถ้าถูกถามว่าถ้าข้าม UI ไปยิง SQL ตรง ๆ จะเกิดอะไร: trigger R5 ปฏิเสธ)

## 19 · พนักงาน: ตารางเวร และ “ใครเป็นคนทำ”
*เวลาโดยประมาณ 1:00* · **เปิดเว็บ → Schedules (ตารางเวรรายสัปดาห์) · แล้วเปิด Attendance**

ฝั่งซ้าย: โมดูลกำลังคน
- SHIFT เป็นของสาขา (กะเช้า กะดึก ฯลฯ)
- WORK_SCHEDULE คือ “ใครเข้ากะไหน วันไหน” — เป็นตารางที่เชื่อม EMPLOYEE กับ SHIFT
- ATTENDANCE คือเวลาเข้า–ออกจริง ต่อหนึ่งตารางเวร มีได้ไม่เกิน 1 แถว (schedule_id เป็น UNIQUE)
- จุด normalization: ATTENDANCE ไม่เก็บ employee_id เพราะหาได้จาก schedule_id → WORK_SCHEDULE.employee_id อยู่แล้ว ถ้าเก็บซ้ำจะเสี่ยงข้อมูลขัดกัน (3NF)
- R21: กะของพนักงานคนเดียวกันห้ามทับเวลากัน · R22: สถานะ (ตรงเวลา/สาย/ขาด) คำนวณจากเวลาจริง ไม่ให้คนกรอกเอง

ฝั่งขวา: actor FK 10 เส้น ที่บอกว่าใครเป็นคนทำ เช่น ใครรับเงิน ใครเช็คอินให้ ใครตรวจงานแม่บ้าน — ใน ERD วาดเป็นเส้นประ
- 9 ใน 10 เป็น NULL ได้ (เช่น ลูกค้าจองเองทางเว็บ ไม่มีพนักงานสร้าง) ยกเว้น reported_by_emp_id ของงานซ่อมที่ต้องมีคนแจ้งเสมอ
- trigger รู้ว่าใครทำ เพราะทุกการเขียนผ่าน withTx(session) ซึ่งตั้งค่าพนักงานที่ทำรายการไว้ใน transaction

เดโม: Schedules → ตารางเวรรายสัปดาห์ → Attendance

## 20 · Normalize ถึง 3NF แล้วตั้งใจเก็บซ้ำ 2 จุด
*เวลาโดยประมาณ 1:00* · **เปิดเว็บ → Bookings › BK-0001 · ชี้ยอดรวม 4 ช่อง ที่ trigger คำนวณให้**

ไล่ทีละขั้นสั้น ๆ:
- 1NF: ไม่มีช่องที่เก็บหลายค่า — amenities ที่ร่างแรกเป็นข้อความยาว แตกเป็น ROOM_TYPE_AMENITY, ผู้เข้าพักแตกเป็น GUEST, สิทธิ์แตกเป็น ROLE_PERMISSION
- 2NF: ตารางที่ PK มี 2 คอลัมน์ (ROLE_PERMISSION, ROOM_TYPE_AMENITY, EMPLOYEE_SERVICE_SKILL) คอลัมน์ที่เหลือขึ้นกับทั้งสองคอลัมน์
- 3NF: แยก MEMBER_TIER ออกมา, ATTENDANCE ไม่มี employee_id (หาผ่าน schedule), REVIEW ไม่มี customer_id (หาผ่าน booking)

ส่วนที่จงใจไม่ normalize เข้ม (controlled denormalization) มี 2 แบบ:
1) Snapshot — ราคาต่อคืน ราคาบริการ และอัตราส่วนลดสมาชิก ถูก copy มาเก็บตอนจอง เพราะความจริงทางธุรกิจคือ “ราคา ณ วันจอง” ไม่ใช่ราคาปัจจุบัน
2) Stored totals และ tier — เก็บยอดรวมไว้เพื่อให้อ่านเร็วและตรวจย้อนได้ แต่ให้ trigger เป็นคนเขียนเท่านั้น (ADR-003) และ tier ขยับตามแต้มด้วย trigger R13 (ADR-006) แอปจึงทำให้ข้อมูลขัดกันเองไม่ได้

เดโม: เปิด BK-0001 แล้วชี้ยอด room_total, service_total, discount_amount, grand_total

## 21 · สิ่งที่ FK บังคับไม่ได้ ให้ trigger บังคับ
*เวลาโดยประมาณ 1:30* · **เปิดเว็บ → Availability (BKK · 14 คืน) → กด + ในคืนว่าง → Create booking**

ข้อความหลัก: FK บอกได้แค่ว่า “แถวแม่มีอยู่จริง” แต่กฎธุรกิจหลายข้อต้องดูข้ามแถวหรือข้ามตาราง จึงต้องใช้ constraint แบบอื่นและ trigger — มีทั้งหมด R1–R22 ใน 44 triggers และทุกข้อมีเทสต์ใน db/tests

- R1 ใช้ EXCLUDE constraint ซึ่งเป็นของ PostgreSQL โดยเฉพาะ (gist + daterange)
- R3 ล็อกแถวห้องด้วย SELECT … FOR UPDATE ก่อนตรวจการทับวัน
- R11 เป็น deferred constraint trigger ตรวจตอน COMMIT เพราะห้องถูกเพิ่มเข้าใบจองทีละห้อง ถ้าตรวจทันทีจะผิดระหว่างทาง
- R17 ล็อกใบจองตอนรับเงิน ไม่ให้สองคนรับเงินซ้อนกันจนเกินยอด
- ผิดกฎ → RAISE EXCEPTION (SQLSTATE P0001) พร้อมข้อความภาษาคน → API แปลงเป็น 422 → หน้าเว็บแสดงข้อความนั้นตรง ๆ

ทำไมกันจองชนได้: หน้า Availability ใช้เงื่อนไขทับวันแบบเดียวกับ R3 ก็จริง แต่คนตัดสินสุดท้ายคือ trigger ในฐานข้อมูล ถ้าสองเคาน์เตอร์เห็นห้องว่างพร้อมกันแล้วกดจอง คนที่สองต้องรอ lock และจะเห็นใบจองของคนแรก จึง rollback

เดโม: Availability → เลือก BKK, 14 คืน → อธิบายแถบ booking และ Free rooms → กด + ในคืนว่าง → ฟอร์มจองถูกกรอกให้ → อธิบาย R3 / R11 / R12 และราคา snapshot (ไม่ต้อง submit ถ้าเวลาน้อย)

## 22 · ทั้ง 31 ตาราง มีหน้าเว็บของตัวเอง
*เวลาโดยประมาณ 1:00* · **เปิดเว็บ → Bookings › BK-0001 · หน้าเดียวที่ดึงจากหลายตารางลูก**

หน้านี้ตอบส่วนสุดท้ายของคำถามที่ 5: ER Diagram เชื่อมกับหน้าเว็บอย่างไร

- ทุกตารางทั้ง 31 ตารางมีหน้าเว็บที่อ่านหรือเขียนมันอยู่ จัดกลุ่มตามเมนูซ้ายเดียวกับ 7 โมดูลใน ERD
- ตารางนี้ไม่ได้ทำขึ้นมาเพื่อสไลด์ — อยู่ในโค้ดจริงที่ app/lib/nav.ts ซึ่งแต่ละเมนูระบุว่าใช้ตารางไหน และระบุ permission ที่ต้องมีเพื่อเห็นเมนูนั้น
- ตารางลูกส่วนใหญ่ไม่มีเมนูของตัวเอง แต่โผล่ในหน้า detail ของแม่ เช่น room_image อยู่ในหน้า detail ของห้อง และ booking_room, guest, booking_service, payment, booking_status_log อยู่ในหน้า detail ของใบจอง — นี่คือความสัมพันธ์ 1 : N ที่กลายเป็นหน้าจอ
- ตารางกลาง M:N มักกลายเป็น matrix หรือ checkbox เช่น role_permission คือ matrix สิทธิ์ในหน้า Roles & Permissions

เดโม: เปิด BK-0001 แล้วชี้ทีละส่วนว่ามาจากตารางไหน

## 23 · ฐานข้อมูลเป็นคนตัดสินสุดท้าย
*เวลาโดยประมาณ 0:30*

สรุปหนึ่งประโยค: เราออกแบบให้ความสัมพันธ์และกฎธุรกิจอยู่ในฐานข้อมูล แอปจึงทำข้อมูลผิดไม่ได้แม้จะมีบั๊ก

ถ้ามีเวลา: เปิด terminal รัน npm run db:test ให้เห็น 58 passed (รัน npm run db:reset ก่อน เพราะเทสต์บางข้ออิงวันที่ปัจจุบัน)

คำตอบสั้นเมื่อถูกถาม:
- กันจองชนอย่างไร: UI ใช้เงื่อนไขทับวันเดียวกับ R3 แต่ trigger ในฐานข้อมูลตัดสินสุดท้ายและล็อกแถวห้อง จึงกัน race condition ได้
- กันข้ามสาขาอย่างไร: ทุก repository รับ branchScope จาก session ผู้ใช้ขยาย scope เองไม่ได้ มีแต่ session ระดับเครือ (owner) ที่สลับสาขาได้
- ยอดเงินคำนวณที่ไหน: trigger คำนวณ room/service/discount/grand total แอปไม่เขียนยอดเอง
- audit อยู่ไหน: trigger ของสถานะใบจองเขียน booking_status_log พร้อมพนักงานที่ทำ (ได้จาก transaction ของ withTx)
- ทำไม raw SQL: วิชานี้ต้องโชว์ constraint, trigger, view, transaction และ query plan ให้เห็นชัด
- ทำไมไม่ลบคอลัมน์ยอดรวมให้เป็น 3NF เข้ม: เป็น controlled denormalization ที่ trigger คุม (ADR-003) ราคาต้องเป็น snapshot ณ วันจอง

เรื่องต่อยอด: schema รองรับการจองจากลูกค้าแล้ว — booking_channel มีค่า WEBSITE และ created_by_emp_id เป็น NULL ได้ ที่ยังขาดคือหน้าเว็บฝั่งลูกค้า, ระบบ login ของลูกค้า และ API สำหรับลูกค้า
